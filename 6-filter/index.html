    filter

    如前一章所述，過濾器是可用於將內容導入或導出到LibreOffice文檔中或從中導出的對象。API定義了兩個服務com.sun.star.document.ImportFilter和com.sun.star.document.ExportFilter。過濾器實現可以支持其中一個或兩個。如果使用只支持導入的特定過濾器，導入的文檔被用戶修改，然後用戶按下"保存"按鈕，將執行"另存為"操作，因為LibreOffice必須假設過濾器組件是"僅導入"的，所以存儲必須以不同的格式進行。對同一內容有不同的導出過濾器沒有幫助。如果應該可能直接"保存"操作，則必須在同一過濾器對象處支持兩個過濾器服務。

    過濾器是從工廠服務com.sun.star.document.FilterFactory創建的。該服務還提供對知道LibreOffice所有註冊過濾器及其屬性的配置的低級訪問，支持搜索和查詢功能，並創建和初始化過濾器組件。例如，如果知道內容的類型名稱，可以使用在FilterFactory的查詢來檢索可能過濾器的一個或多個內部過濾器名稱，然後在選擇其中一個後使用此名稱創建過濾器。

    注意： 許多現有的過濾器是遺留過濾器。組件加載器或XStorable實現不使用FilterFactory創建它們，而是通過內部C++調用觸發過濾。因此，要求FilterFactory創建這樣的過濾器是不可能的。

    如果過濾器實現接口com.sun.star.lang.XInitialization，則可以初始化過濾器。過濾器工廠服務在創建過濾器對象後、在將過濾器返回給請求過濾器的代碼之前，直接使用initialize()方法。它將過濾器的配置數據以及由工廠的創建請求指定的所有參數和選項傳遞給工廠。這些屬性通常來自MediaDescriptor的"FilterOptions"屬性，並且要么是由請求加載或存儲的代碼放置在那裡，要么是由用戶在過濾器選項對話框中輸入的內容放置在那裡。如何實現這樣的過濾器對話框在關於過濾器選項的章節中解釋。

    initialize()的參數列表使用以下協議：

    • 列表中的第一項是com.sun.star.beans.PropertyValue結構的序列，描述過濾器的配置屬性。
    • 所有其他項目直接從工廠接口方法createInstanceWithArguments()的參數Arguments複製。

    警告： 接口提供了讀取和寫入此名稱的功能。在LibreOffice的運行時間內不允許更改內部過濾器名稱，因為所有過濾器名稱必須是唯一的，過濾器實例不可能更改其名稱。對setName()的調用應該被忽略或轉發到FilterFactory服務，該服務知道所有唯一名稱並可以解決歧義！

    過濾器獲得自己的名稱作為參數的事實可以用來使一個過濾器實現在配置中充當多個過濾器。這在以下過濾器初始化實現的代碼片段中顯示：

    private String m_sInternalName;
public void initialize( Object[] lArguments )
        throws com.sun.star.uno.Exception
{
        // no arguments - no initialization
        if (lArguments.length<1)
                return;
        // Arguments[0] = own configuration data
        com.sun.star.beans.PropertyValue[] lConfig =
                (com.sun.star.beans.PropertyValue[])lArguments[0];

        // Arguments[1..n] = optional arguments of create request
        for (int n=1; n<lArguments.length; ++n)
        {
                ...
        }

        // analyze own configuration data for our own internal
        // filter name! Important for generic filter services,
        // which are registered more then once. They can use this
        // information to find out, which specialization of it
        // is required.
        for (int i=0; i<lConfig.length; ++i)
        {
                if (lConfig[i].Name.equals("Name"))
                {
                        m_sInternalName =
                                AnyConverter.toString(lConfig[i].Value);

                        // Tip: A generic filter implementation can use this internal
                        // name at runtime, to detect which specialization of it is required.
                        if (m_sInternalName =="filter_format_1")
                                m_eHandle = E_FORMAT_1;
                        else
                        if (m_sInternalName =="filter_format_2")
                                ...
                }
        }
}

    在一個工作流程中，過濾器可以作為導入或導出過濾器。如果加載內容，過濾器的創建者將使用com.sun.star.document.XImporter接口及其方法setTargetDocument()將過濾器綁定到它應該導入到的文檔。如果存儲內容，接口com.sun.star.document.XExporter及其方法setSourceDocument()將過濾器綁定到它應該從中獲取數據的文檔。過濾過程在兩種情況下都由相同的方法完成：它是com.sun.star.document.XFilter接口的filter()方法，兩種過濾器都必須支持。這裡將MediaDescriptor傳遞給過濾器。

    提示： 在同時實現導入和導出的對象中，有必要決定調用filter()方法時是要求導入還是導出。區分因素是之前是調用了setTargetDocument還是setSourceDocument（見下面的示例代碼）。過濾器的用戶負責按有效順序進行此調用。

    這個示例代碼顯示了如何在過濾器實現中輕鬆跟踪所需的過濾器操作：

    private boolean m_bImport;

// used to tell us: "you will be used for import"
public void setTargetDocument(
  com.sun.star.lang.XComponent xDocument )
    throws com.sun.star.lang.IllegalArgumentException
{
    m_bImport = true;
}

// used to tell us: "you will be used for export"
public void setSourceDocument(
  com.sun.star.lang.XComponent xDocument )
    throws com.sun.star.lang.IllegalArgumentException
{
    m_bImport = false;
}

// detect required type of filter operation
public boolean filter(
  com.sun.star.beans.PropertyValue[] lDescriptor )
{
      boolean bState;
      if (m_bImport)
        bState = impl_import( lDescriptor );
      else
        bState = impl_export( lDescriptor );
      return bState;
}
