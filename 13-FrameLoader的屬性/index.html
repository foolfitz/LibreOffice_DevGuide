    基於XML的過濾器開發

    基於XML的過濾器開發

    簡介

    本章概述了使用XML過濾器適配器框架的基於XML的過濾組件的開發。更多信息也可在https://www.openoffice.org/xml/filter/獲取。XML過濾器適配器是com.sun.star.document.XFilter的通用實現。它被設計為可重用的，並提供設計和引用基於XML的導入和導出過濾器的標準方法。XML過濾器適配器本身不執行任何過濾功能，而是用於實例化過濾組件。

    XML過濾器適配器框架的優點是你不必使用文檔模型從導入文件創建文檔，也不必迭代文檔模型將其導出到不同的文件格式。相反，你可以使用LibreOffice XML文件格式進行導入和導出。導入時，你解析導入文件並將LibreOffice XML發送到過濾器適配器，它會在GUI中為你創建文檔。導出時，辦公室會發送當前文檔的描述作為LibreOffice XML，這樣你就可以導出而不必迭代文檔模型。

    如過濾器章節所述，過濾器通過其方法filter()工作。在基於XML的過濾器的情況下，此方法由XML過濾器適配器實現。基於其"UserData"屬性，它實例化XML導入過濾器並使用其方法importer()傳遞源的MediaDescriptor、LibreOffice XML的專用XML文檔處理程序和用戶數據。導入過濾器必須讀取導入源並將LibreOffice XML傳遞給在importer()調用中接收的文檔處理程序，模擬調用解析器回調函數的SAX解析器。

    在導出過濾器的情況下，相同的filter()調用將使用"UserData"屬性實例化XML導出過濾器並使用其方法exporter()傳遞目標位置和用戶數據。在這種情況下，辦公室期望導出過濾器是com.sun.star.xml.sax.XDocumentHandler，能夠處理LibreOffice XML。辦公室創建帶有LibreOffice XML的導出流，並解析此XML，以便導出過濾器接收SAX回調並可以將它們翻譯成任何必要的內容，將結果寫入在exporter()調用中接收的目標。

    示例實現

    有Java和C++實現的_Flat LibreOffice XML_讀取器和寫入器，它們使用XML過濾器適配器。這些旨在作為示例過濾器組件實現，並提供了一個骨架過濾器組件，可以由希望創建自己的過濾組件的開發者擴展。它們託管在git中

    odk/examples/DevelopersGuide/OfficeDev/FilterDevelopment/FlatXmlFilter_java

    和

    odk/examples/DevelopersGuide/OfficeDev/FilterDevelopment/FlatXmlFilter_cpp

    編寫過濾組件

    過濾組件必須實現以下接口，如com.sun.star.xml.ImportFilter服務和com.sun.star.xml.ExportFilter服務所描述：

    導入器：

    com.sun.star.xml.XMLImportFilter

    導出器：

    com.sun.star.xml.XMLExportFilter和com.sun.star.xml.sax.XDocumentHandler

    XImportFilter

    服務com.sun.star.xml.XMLImportFilter定義了一個具有以下方法的接口：

    boolean importer(
[in] sequence< com::sun::star::beans::PropertyValue > aSourceData,
[in] com::sun::star::xml::sax::XDocumentHandler xDocHandler,
[in] sequence< string > msUserData )

    aSourceData是一個MediaDescriptor，可用於獲取以下信息：

    • 一個XInputStream
    • 這是一個附加到要讀取的源的流。這可以是文件或其他一些數據源。
    • Filename
    • 這是磁盤上文件的名稱，輸入流來自於此。
    • Url
    • 這是描述正在讀取的位置的URL。

    xDocHandler是在解析XInputStream時可以使用的SAX事件處理程序，它可能包含或不包含LibreOffice XML。在LibreOffice可以讀取此流之前，需要將其轉換為LibreOffice XML。

    msUserData是Strings數組，包含在TypeDetection.xcu文件中的Filter定義的UserData部分提供的信息。

    XExportFilter

    com.sun.star.xml.XExportFilter定義了一個具有以下方法的接口：

    boolean exporter(
[in] sequence< com::sun::star::beans::PropertyValue > aSourceData,
[in] sequence< string > msUserData )

    aSourceData和msUserData包含與導入器中相同類型的信息，只是MediaDescriptor包含一個XOutputStream，可用於寫入。

    XDocumentHandler

    當導出發生時，新的過濾組件還必須是一個XDocumentHandler，以允許基於SAX事件的輸出被過濾（如果需要）。因此，exporter不傳遞XDocumentHandler，任何由XML過濾器適配器使用的導出器都必須實現com.sun.star.xml.sax.XDocumentHandler接口。

    注意： 為了使基於Java的組件有效運作，一組包裝器類已添加到javaunohelper包中。這些文件允許使用與普通Java InputStream或OutputStream相同的方法訪問XInputStream或XOutputStream。這些類位於javaunohelper包中： - com.sun.star.lib.uno.adapter.XInputStreamToInputStreamAdapter - com.sun.star.lib.uno.adapter.XOutputStreamToOutputStreamAdapter

    有關這些助手類用法的更多信息，請參見flatxmljava示例。

    導入器

    評估XImportFilter參數

    編寫導入器通常從從MediaDescriptor和userData中提取所需變量開始。這些變量對於過濾組件正確操作是必需的。根據單個過濾器的需求，首先要做的是從稱為接口定義中的aSourceData的MediaDescriptor提取信息。這可以通過以下方式實現：

    獲取MediaDescriptor中的元素數量

    sal_Int32 nLength = aSourceData.getLength();

    遍歷MediaDescriptor以找到所需的信息：輸入流，文件名或URL。

    for (sal_Int32 i = 0; i < nLength; i++) {
        if (pValue[i].Name == "InputStream")
                pValue[i].Value >>= xInputStream;
        else if (pValue[i].Name == "FileName")
                pValue[i].Value >>= sFileName;
        else if (pValue[i].Name == "URL")
                pValue[i].Value >>= sURL;
}

    傳遞給importer()的msUserData參數包含定義過濾器如何操作的信息，因此必須根據需要引用此信息。

    導入器過濾

    現在已經獲得了一個包含所有要處理信息的XInputStream實現。從過濾角度來看，您可以從這個流中讀取並執行任何必要的處理，以便將輸入轉換為LibreOffice XML。一旦完成，您需要將結果寫入可以解析為LibreOffice內部格式的地方。可以使用Pipe來實現這一點。Pipe是一種可以寫入和讀取的緩衝形式。對於導入器，從從MediaDescriptor提取的XInputStream讀取，一旦過濾完成，寫入已創建的Pipe。在進行解析時可以讀取這個Pipe。以下是如何創建Pipe：

    Reference <XInterface> xPipe;

// We Create our pipe
xPipe= XflatXml::xMSF->createInstance(OUString::createFromAscii("com.sun.star.io.Pipe"));

// We get an inputStream to our Pipe
Reference< com::sun::star::io::XInputStream > xPipeInput (xPipe,UNO_QUERY);

// We get an OutputStream to our Pipe
Reference< com::sun::star::io::XOutputStream > xTmpOutputStream (xPipe,UNO_QUERY);

    可以從XInputStream讀取，可以向XOutputstream寫入。

    解析結果

    一旦產生了所需的LibreOffice XML並將其寫入Pipe的XOutputStream，就可以在XDocumentHandler的幫助下解析Pipe的XinputStream。

    // Create a Parser
const OUString sSaxParser("com.sun.star.xml.sax.Parser");
Reference < com::sun::star::xml::sax::XParser > xSaxParser(xMSF->createInstance(sSaxParser), UNO_QUERY);

// Create an InputSource using the Pipe
com::sun::star::xml::sax::InputSource aInput;
aInput.sSystemId = sFileName;           // File Name
aInput.aInputStream = xPipeInput;       // Pipe InputStream

// Set the SAX Event Handler
xSaxParser->setDocumentHandler(xHandler);

// Parse the result
try {
  xSaxParser->parseStream(aInput);
}
catch (Exception &exc) {
  // Perform exception handling
}

    假設XML有效，不會拋出異常，導入器將返回true。在這個階段，過濾完成，導入的文檔將顯示出來。

    導出器

    評估XExportFilter參數

    exporter()方法的操作方式與importer()大致相同，只是導出器不使用提供的XDocumentHandler，而是本身是com.sun.star.xml.sax.XDocumentHandler實現。

    當調用exporter()方法時，需要提取過濾器使用的必要變量。這與導入器發生的情況相同，只是MediaDescriptor包含XOutputStream，而不是導入器的XInputStream。一旦提取了變量（在某些情況下創建了Pipe），exporter()方法返回。它在此階段不執行過濾。

    注意： 只有在輸出在由XDocumentHandler處理後需要進一步處理時，才需要pipe。否則，XDocumentHandler實現的結果可以直接寫入提供的XOutputStream。例如，這是FlatXML過濾器的情況。

    導出器過濾

    在exporter()方法返回後，XML過濾器適配器調用com.sun.star.xml.sax.XDocumentHandler方法來解析XML輸出。

    對於過濾，使用com.sun.star.xml.sax.XDocumentHandler實現。這由一組SAX事件處理方法組成，這些方法定義了如何處理特定的XML標籤。這些方法是：

    startDocument() {
}
endDocument() {
}
startElement() {
}
endElement() {
}
charactors() {
}
ignorableWhitespace() {
}
processingInstruction() {
}
setDocumentLocator() {
}

    此事件處理的結果可以處理並寫入從MediaDescriptor提取的XOutputStream。

    XML過濾器檢測

    符合不同DTD規範的XML文件數量意味著單一過濾器和文件類型定義不足以處理所有可能的可用格式。為了允許LibreOffice處理多個過濾器定義和實現，有必要實現一個額外的過濾器檢測模塊，該模塊能夠根據其DocType聲明確定正在讀取的XML文件的類型。

    為了實現這一點，可以實現一個過濾器檢測服務com.sun.star.document.ExtendedTypeDetection，它能夠處理和區分許多不同的基於XML的文件格式。這種類型的服務取代了使用文件後綴來確定類型的基本flat檢測，而是執行deep檢測，使用文件的內部結構和內容來檢測其真實類型。

    深度檢測的要求

    實現能夠識別一個或多個唯一XML類型的深度檢測模塊有三個要求。這些包括：

    • 用於更詳細描述格式的擴展類型定義（TypeDetection.xcu）。
    • DetectService實現。
    • DetectService定義（TypeDetection.xcu）。

    擴展文件類型定義

    由於許多不同的XML文件可以符合不同的DTD，特定XML文件的類型定義需要擴展。為此，可以將部分或全部DocType信息包含為文件類型定義的一部分。此信息作為類型節點的ClipboardFormat屬性的一部分持有。唯一的命名空間或前言在序列中的這一點識別字符串為DocType聲明。

    示例類型定義：

    <node oor:name="writer_DocBook_File" oor:op="replace">
    <prop oor:name="UIName">
        <value XML:lang="en-US">DocBook</value>
    </prop>
    <prop oor:name="Data">
        <value>0,,doctype:-//OASIS//DTD DocBook XML V4.1.2//EN,,XML,20002,</value>
    </prop>
</node>

    ExtendedTypeDetection服務實現

    為了使類型檢測代碼作為ExtendedTypeDetection服務運行，您必須實現com.sun.star.document.XExtendedFilterDetection接口定義中定義的detect()方法：

    string detect( [inout]sequence<com::sun::star::beans::PropertyValue > Descriptor );

    此方法為您提供了一個PropertyValue序列，您可以從中提取當前的TypeName和正在加載的文件的URL：

    ::rtl::OUString SAL_CALL FilterDetect::detect(com::sun::star::uno::Sequence< com::sun::star::beans::PropertyValue >& aArguments )
{
const PropertyValue * pValue = aArguments.getConstArray();
sal_Int32 nLength;
::rtl::OString resultString;
nLength = aArguments.getLength();
for (sal_Int32 i = 0; i < nLength; i++) {
        if (pValue[i].Name == "TypeName") {
        }
        else if (pValue[i].Name == "URL") {
                pValue[i].Value >>= sUrl;
        }
}

    一旦您有了文件的URL，您可以使用它創建一個::ucb::Content，從中可以打開文件的XInputStream：

    Reference< com::sun::star::ucb::XCommandEnvironment > xEnv;
::ucb::Content aContent(sUrl,xEnv);
xInStream = aContent.openStream();

    現在可以使用這個XInputStream讀取正在加載的文件的標頭。由於文件中DocType信息的確切位置未知，將讀取前1000字節的信息：

    ::rtl::OString resultString;
com::sun::star::uno::Sequence< sal_Int8 > aData;
long bytestRead = xInStream->readBytes (aData, 1000);
resultString = ::rtl::OString( (const char *)aData.getConstArray(), bytestRead);

    一旦有了這些信息，就可以開始尋找描述正在加載的文件的類型。為此，需要獲取當前支持的類型列表：

    Reference <XNameAccess> xTypeCont(mxMSF->createInstance(OUString::createFromAscii(
                                "com.sun.star.document.TypeDetection" )),UNO_QUERY);
Sequence <::rtl::OUString> myTypes= xTypeCont->getElementNames();
nLength = myTypes.getLength();

    對於這些類型中的每一個，必須首先確定ClipboardFormat屬性是否包含DocType：

    Loc_of_ClipboardFormat=...;
Sequence<::rtl::OUString> ClipboardFormatSeq;
Type_Props[Loc_of_ClipboardFormat].Value >>=ClipboardFormatSeq ;
while() {
        if(ClipboardFormatSeq.match(OUString::createFromAscii("doctype:") {
                    //if it contains a DocType, start to compare to header
        }
}

    可以檢查文件類型的所有可能的DocType聲明以確定匹配。如果找到匹配，則返回與匹配相對應的類型。如果找不到匹配，則返回空字符串。這將強制LibreOffice進入平面檢測模式。

    TypeDetection.xcu DetectServices條目

    現在您已經創建了ExtendedTypeDetection服務實現，需要告訴LibreOffice何時使用此服務。

    首先創建一個DetectServices節點（除非已經存在一個），然後添加有關已實現的檢測服務的特定信息，即服務的名稱和使用它的文件類型。

    <node oor:name="DetectServices">
<node oor:name="com.sun.star.comp.filters.XMLDetect" oor:op="replace">
        <prop oor:name="ServiceName">
                <value XML:lang="en-US">com.sun.star.comp.filters.XMLDetect</value>
        </prop>
        <prop oor:name="Types">
                <value>writer_DocBook_File</value>
                <value>writer_Flat_XML_File</value>
        </prop>
</node>
</node>
